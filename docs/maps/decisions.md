# 결정 기록

## DR-01 — 서울 판별과 보존 범위

- 결정: `nvidia/Nemotron-Personas-Korea`의 `train`에서 `province`가 정확히 `서울`인 모든 행을 선택하고, `district`를 포함한 원본 26개 필드와 원본 행 순서를 보존한다.
- 분류/근거: SELF. 원본의 시도 필드가 서울 여부를 직접 나타내며, 사용자가 요청한 서울 지역 부분집합을 데이터 손실 없이 제공한다.
- 대안: `district` 문자열 추측이나 특정 구만 선택하는 방법은 지역 표기를 임의 해석하거나 요청 범위를 좁힐 수 있으므로 기각한다.
- 날짜: 2026-10-30

## DR-02 — 원본 버전과 저장 형식

- 결정: 원본 커밋 `ada0f5b53a38bb5a30cce09358adde883c1ab63a`의 Parquet 9개를 입력으로 사용하고 서울 행을 하나의 Parquet 파일로 저장한다.
- 분류/근거: SELF. 원본과 같은 형식으로 타입과 컬럼을 보존하고, 버전을 고정하면 검증과 재현이 가능하다. 데이터셋은 사용자가 지정한 공개 소스다.
- 대안: CSV/JSON으로 변환하거나 이동하는 최신 브랜치를 참조하는 방법은 타입 보존과 재현성 면에서 기각한다.
- 날짜: 2026-10-30

## DR-03 — 처리와 검증

- 결정: 원본 조각을 하나씩 임시 다운로드해 공식 SHA-256과 크기를 검사하고, 배치별 필터 후 임시 원본을 삭제한다. 결과의 전체 행 내용, 서울 조건, 중복 ID, 원본과 결과의 행 수를 검증한 다음 최종 파일로 확정한다.
- 분류/근거: SELF. 순수 내부 처리이며 다운로드 누락과 손상, 부분 저장을 감지한다.
- 대안: 불완전한 결과를 그대로 저장하거나 검증 없이 전체 조각을 보관하는 방법은 기각한다.
- 날짜: 2026-10-30

## DR-04 — 활동 엔진의 용도와 데이터 범위

- 결정: `nvidia/Nemotron-Personas-Korea` 데이터만 사용해 가상 페르소나의 활동을 시뮬레이션한다. 외부 생활시간 통계나 실제 개인의 행동 기록은 입력으로 사용하지 않는다.
- 분류/근거: ASK, 사용자 확정. 사용자가 “이 데이터로만 시뮬레이션”한다고 답했다. 시간 정보가 없는 부분은 데이터에서 관측된 사실이 아니라 시뮬레이션 가정으로 구분한다.
- 대안: 외부 통계로 보정한 인구 집단 예측, 실제 개인의 행동 추정은 이번 범위에서 제외한다.
- 후속: 구조화 필드와 지리 상수의 사용 해석은 [DR-14](#dr-14--구조화-필드의-사용과-근거-우선순위), [DR-13](#dr-13--장소-해석과-지리-상수)에서 명문화했다. 이 결정의 문구는 유지한다.
- 날짜: 2026-10-30

## DR-05 — 활동 출력 방식

- 결정: 시간대별로 각 지역에 속한 모든 페르소나의 행동 상태를 스냅샷으로 만들어 프레임화한다. 시간 간격, 지역 귀속 기준과 생성·보관 방식은 별도 결정이 필요하다.
- 분류/근거: ASK, 사용자 확정. 사용자가 “시간대별 각 지역의 모든 개인의 행동을 snapshot을 일일이 떠서 프레임화”한다고 답했다.
- 대안: 특정 인물의 요청 시 하루 일정을 생성하는 방식이나 시간대별 확률만 반환하는 방식은 주 출력이 아니다.
- 후속: 지역 귀속 기준과 간격은 각각 DR-07, DR-08에서 확정했다. 생성·보관 방식은 미확정이었으나 [DR-18](#dr-18--저장과-조회-방식)에서 확정했다.
- 날짜: 2026-10-30

## DR-06 — 지리적 범위

- 결정: 이번 시뮬레이션은 서울 페르소나만 다룬다. 원본 선택 조건은 기존 [DR-01](#dr-01--서울-판별과-보존-범위)의 `province == '서울'`이다.
- 분류/근거: ASK, 사용자 확정. 사용자가 서울만 사용하는 선택지를 선택했다. 지역별 프레임에서 지역의 뜻은 추가 확인이 필요하다.
- 대안: 전국 동시 처리 또는 전국 설계 후 서울 우선 검토는 이번 범위에서 제외한다.
- 후속: 프레임의 지역 의미는 DR-07에서 현재 활동 구로 확정했다.
- 날짜: 2026-10-30

## DR-07 — 지역별 프레임의 의미

- 결정: 지역별 프레임은 거주 구가 아니라 시뮬레이션상 현재 활동 중인 구를 기준으로 구성한다. 이동과 활동 장소는 원문에서 알 수 없으면 명시적 가정으로 생성한다.
- 분류/근거: ASK, 사용자 확정. 사용자가 “현재 활동 구별 프레임”을 선택했다. 원본 `district`는 거주지 단서이므로 현재 위치와 별도로 보존한다.
- 대안: 활동 위치와 관계없이 원본 거주 구로 묶는 방식은 기각했다.
- 후속: 근거 없는 장소의 배치와 이동 길이는 [DR-13](#dr-13--장소-해석과-지리-상수)에서 확정했다.
- 날짜: 2026-10-30

## DR-08 — 시뮬레이션 프레임 간격

- 결정: 10분 간격, 하루 144프레임을 사용한다.
- 분류/근거: ASK, 사용자 확정. 사용자가 10분 선택지를 선택했다.
- 대안: 30분과 1시간 간격은 기각했다.
- 후속: 시각 눈금과 프레임 의미는 [DR-17](#dr-17--프레임과-시간-규약-및-결정성)에서 확정했다.
- 날짜: 2026-10-30

## DR-09 — 원문에 없는 시간대의 활동

- 결정: 각 페르소나의 빈 시간은 일반 활동 등의 시뮬레이션 가정으로 채우고, 원문에 있는 내용과 구분해 표시한다.
- 분류/근거: ASK, 사용자 확정. 사용자가 “가정으로 빈 시간 채우기”를 선택했다.
- 대안: 원문 근거가 없는 시간대를 모두 미상으로 두는 방식은 기각했다. 생성 실패나 해결되지 않은 모순의 예외 처리는 별도 설계가 필요하다.
- 후속: 미상 장소와 상충 단서의 예외 처리는 [DR-12](#dr-12--서울-밖-활동의-범위와-판정), [DR-14](#dr-14--구조화-필드의-사용과-근거-우선순위)에서, 빈 시간의 기본값은 [DR-19](#dr-19--기본-일과-템플릿)에서 확정했다.
- 날짜: 2026-10-30

## DR-10 — 서울 외 활동의 처리

- 결정: 시뮬레이션에 포함된 모든 인물의 현재 활동 구를 항상 서울 안으로 유지한다. 원문에 서울 밖 활동이 명시되면 해당 서울 밖 여행 단서를 시뮬레이션에서 생략한다.
- 분류/근거: ASK, 사용자 확정. 사용자가 “항상 서울 안에만 유지”를 선택했다. 생략 사실은 추적 가능하게 기록하고 원본 텍스트는 보존한다.
- 대안: 서울 밖 활동을 별도 버킷으로 표시하는 방식은 기각했다.
- 후속: 범위와 판정 단계는 [DR-12](#dr-12--서울-밖-활동의-범위와-판정)에서 명문화했다. 결정은 유지한다.
- 날짜: 2026-10-30

## DR-11 — 이동 중 지역 귀속

- 결정: 구 사이 이동 중 전반부에는 출발 구, 후반부에는 도착 구 프레임에 귀속한다. 이는 실제 경계 통과 위치가 아니라 시뮬레이션 규칙이다.
- 분류/근거: ASK, 사용자 확정. 사용자가 “이동 전반은 출발 구, 후반은 도착 구”를 선택했다. 원본에 경로·거리·구 경계 통과 시각은 없다.
- 대안: 이동 중에는 출발 구에만 두고 종료 시 도착 구로 이동시키는 방식은 기각했다.
- 후속: 중점 시각의 귀속과 최소 이동 길이는 [DR-17](#dr-17--프레임과-시간-규약-및-결정성)에서 확정했다.
- 날짜: 2026-10-30

## DR-12 — 서울 밖 활동의 범위와 판정

- 결정: [DR-10](#dr-10--서울-외-활동의-처리)을 유지하면서 다음을 명문화한다. ① 범위: "서울 밖 활동"은 여행·캠핑·나들이뿐 아니라 서울 밖 출퇴근·출장·행사·해외를 포함한다. 서울 밖 근무지는 서울 안의 가정 근무지로 대체한다([DR-13](#dr-13--장소-해석과-지리-상수)). ② 판정 단계(`place_scope`): `SEOUL_DISTRICT`(서울 구 확정), `SEOUL_UNSPECIFIED`(서울 안이나 구 미상), `OUTSIDE_SEOUL`(서울 밖 확정: 서울 밖 지명, 해외 국가·도시, '전국·지방·해외' 같은 일반어, 또는 여행·캠핑·펜션·리조트·드라이브 같은 외출형 키워드가 있고 서울 지명이 없는 경우), `UNRESOLVED`(판별 불가: 사전에 없는 지명), `NONE`(장소 단서 없음). 서울 구 후보가 하나라도 있는 지명(예: 일부만 서울에 걸친 산)은 서울로 본다. ③ 처리: `OUTSIDE_SEOUL` 후보는 시뮬레이션에서 생략하고 원문 범위와 제외 사유(`OUTSIDE_SEOUL:<토큰>`)를 남긴다. 한 문장에 서울 안 활동이 함께 있으면 그 부분은 유지한다. `UNRESOLVED`는 활동을 유지하되 장소를 미상으로 두고 C-06의 가정 규칙으로 서울 안에 배치하며, 원문 장소를 서울의 특정 장소로 표시하지 않는다. ④ 지표: 실행마다 서울 밖으로 생략된 단서의 인물 비율과 후보 비율을 보고한다.
- 분류/근거: ASK, 사용자 위임('전부 해결해', 2026-10-30). 검토에서 서울 밖 지명이 있는 인물이 `travel_persona`만 보아도 99,293명(53.6%), 전 필드 합산 64.9%(해외 12.3%)로 나왔다(단어 목록 기준 거친 하한값). 사용자는 이 수치를 확인한 뒤 추천안(DR-10 유지, 범위 명문화, 생략 비율 보고)을 위임했다. 모든 인물을 항상 서울 안에 둔다는 DR-10의 원칙을 일관되게 지키려면 서울 밖 출퇴근도 포함해야 하고, 생략 비율을 지표로 노출해 과소 대표를 숨기지 않는다.
- 대안: 서울 밖 별도 버킷(DR-10에서 기각); 서울 밖 체류를 서울 출입 구에 귀속(원문에 없는 장소를 만들어내므로 기각); 범위를 '여행'으로 한정(서울 밖 출퇴근자가 서울 밖에 놓여 DR-10에 어긋나므로 기각).
- 날짜: 2026-10-30

## DR-13 — 장소 해석과 지리 상수

- 결정: ① 해석: [DR-04](#dr-04--활동-엔진의-용도와-데이터-범위)의 "이 데이터만"은 행동·생활시간 통계와 개인 기록을 입력으로 쓰지 않는다는 뜻으로 읽는다. 서울의 지명→구 대응과 구 인접 관계는 행동 통계가 아닌 정적 지리 상수이므로 수작업 소형 표로 모델에 포함한다(출처 표기: 행정구역 상식, 행동 통계 아님; 규칙 버전에 포함). ② 지리 상수 3종: (가) 서울 장소 사전(랜드마크·하천·산·공원·시장·동네 → 서울 구 후보 집합), (나) 서울 밖 지명 사전(도·시·군, 해외 국가·도시, 일반어), (다) 서울 25개 구 인접표(무방향, 경계 판정 기준을 표에 명기). 사전 항목은 `token`, `scope`(`SEOUL`/`OUTSIDE`), `districts`(서울 후보 구, `OUTSIDE`이면 빈 집합), `note`를 갖는다. 구축은 데이터 빈도 상위부터 시작한다. 취미 목록의 장소형 토큰은 고유 635개이고 상위 100개가 언급의 96.2%, 상위 200개가 99.0%를 덮는다(2026-10-30 접미사 기반 탐지 실측). 서술 필드의 동네·랜드마크까지 넓혀 누적 95% 이상을 목표로 한다. ③ 구 결정: 활동 문장에 구 이름이 직접 나오면 사전보다 그것을 우선한다. 사전 후보 집합이 거주 구를 포함하면 거주 구, 아니면 후보 중 거주 구와의 인접표 홉 수가 최소인 구, 동률이면 (시드, uuid, 토큰)으로 결정적으로 고른다. ④ 근거 없는 장소의 배치(가정)와 이동 길이는 [DR-19](#dr-19--기본-일과-템플릿)의 설계 상수를 따른다. ⑤ 이동 길이 구간화: 인접표 홉 수로 같은 구 10분, 1홉 20분, 2홉 30분, 3홉 이상 40분(설계 상수이며 실제 교통시간이 아님; 출처 라벨 `assumption`). ⑥ 주장하지 않는 것: 실제 경로·거리·교통시간.
- 분류/근거: ASK, 사용자 위임('전부 해결해', 2026-10-30). 구 이름이 나오는 인물 174,795명(94.4%) 중 본인 구가 아닌 구를 언급한 인물은 689명(0.4%)이고 서울 랜드마크는 약 절반(50.5%, 참고치)이 언급된다. 사전 없이는 C-06의 구 배치가 거의 전부 가정이 된다. 여러 구에 걸친 지명(예: 취미 1위 '북한산 둘레길 산책' 6,309건)은 후보 집합이 필요하다. **DR-04의 해석을 지리 상수까지 허용하는 쪽으로 명문화하는 결정이다.** 원치 않으면 이 DR에 취소선을 긋고 (가)~(다) 없이 거주 구 기본 규칙만 쓰는 대안으로 되돌린다.
- 대안: 사전 없이 데이터만 엄격 적용(거주 구 기본) — 프레임이 거주 분포와 거의 같아져 [DR-07](#dr-07--지역별-프레임의-의미)의 의도를 잃으므로 기각; 모든 구 균등 무작위 목적지 — 지리를 무시하므로 기각; 외부 통근 OD 통계 — DR-04 위반이므로 기각.
- 날짜: 2026-10-30

## DR-14 — 구조화 필드의 사용과 근거 우선순위

- 결정: ① 같은 데이터셋의 구조화 필드(`occupation`, `age`, `sex`, `marital_status`, `military_status`, `family_type`, `housing_type`, `education_level`, `bachelors_field`)는 출처 라벨 `structured`의 근거로 쓸 수 있다. [DR-04](#dr-04--활동-엔진의-용도와-데이터-범위)와 충돌하지 않는다. ② 일과 템플릿([DR-19](#dr-19--기본-일과-템플릿))은 고용 상태(`occupation == '무직'` 여부), 연령대(65세 이상), 현역 여부, 자녀 동거 여부(`family_type`에 '자녀' 포함)로 고른다. 직업 문자열(고유 1,748종)은 키워드 규칙으로 소수의 근무 유형(주간 근무, 교대·야간)에 묶고, 판별 불가이면 주간 근무로 두며 적용한 규칙을 기록한다. ③ 상충 시 우선순위: (1) 서술의 현재형 명시 시각(등급 A/B) → (2) 서술의 현재형 시간대어·빈도·요일 → (3) 구조화 필드 기반 템플릿 → (4) 기본 템플릿(가정). 서술의 과거·희망·부정·가정형은 어느 단계에도 쓰지 않고 제외 사유를 남긴다. 구조화 필드와 서술이 충돌하면(예: 무직인데 현재형 '출근') 서술을 우선하되 `conflict` 플래그로 기록한다. 같은 단계 안의 상충(서로 다른 두 시각)은 필드 신뢰 순서([DR-15](#dr-15--시간-신호-해석과-추출-방식))로 정하고 둘 다 기록한다.
- 분류/근거: ASK, 사용자 위임('전부 해결해', 2026-10-30). 무직이 67,302명(36.3%), 65세 이상이 22.2%, 현역이 789명이다. 고용자 117,926명 중 34.2%(40,303명)는 서술에 출근·퇴근·야근·교대 단어가 하나도 없고, 무직의 9.6%(6,483명)는 그런 단어가 있다(과거·희망이거나 상충). 서술 단서만으로는 일과의 뼈대(일하는 날·시간)를 세울 수 없다.
- 대안: 서술 단서만 사용 — 뼈대가 전부 기본값이 되어 기각; 구조화 필드를 서술보다 우선 — 현재형 명시 단서를 버리게 되므로 기각.
- 날짜: 2026-10-30

## DR-15 — 시간 신호 해석과 추출 방식

- 결정: ① 요일 구조 우선: 일과는 평일(월~금)과 주말(토·일) 두 뼈대를 먼저 만들고 주 N회 빈도를 그 안에 배치한다. 공휴일은 v1에서 주말로 바꾸지 않으며, 그 사실을 실행 메타데이터에 기록한다. ② 필드 신뢰: Tier A(현재 습관 위주, 단서를 직접 사용) `hobbies_and_interests`, `sports_persona`, `arts_persona`, `family_persona`; Tier B(모달리티 판정을 통과한 문장만 사용) `professional_persona`, `career_goals_and_ambitions`, `culinary_persona`, `cultural_background`, `persona`, `skills_and_expertise`. `travel_persona`는 [DR-12](#dr-12--서울-밖-활동의-범위와-판정)의 서울 밖 판정 후 남은 문장을 Tier B로 쓴다. `*_list` 두 필드는 활동 어휘로만 쓰고 시간 단서로 쓰지 않는다. 신뢰 순서는 Tier A > Tier B이며 같은 Tier 안에서는 위 나열 순이다. ③ 모달리티: 문장 단위로 `PRESENT_HABIT`, `PAST`, `ASPIRATION`, `NEGATION`, `HYPOTHETICAL`, `UNKNOWN`을 붙인다. 일과 근거는 `PRESENT_HABIT`만이고 `UNKNOWN`은 Tier A 필드에서만 낮은 신뢰의 `PRESENT_HABIT`처럼 쓴다. 목표·희망·가치 진술('~에 집중합니다/가치를 둡니다/추구합니다/만족합니다', 꿈꾸·목표·희망·바라·싶·계획·도전·이루·기대·상상·그리워 등)은 `ASPIRATION`이다. 마커 목록은 규칙 버전에 포함한다. ④ 시각 신뢰 등급: `A` = 시간대어+N시(분)(예: "매일 새벽 6시", "오후 4시쯤"), `B` = 시간대어 없는 N시이나 활동 문맥으로 오전/오후가 확정되는 경우(출근→오전, 퇴근→오후 등), `C` = 시간대어만(아침·오전·오후·저녁·밤·새벽), `D` = 시각 없이 빈도·요일만. 방송명·고유명에 든 숫자('6시 내고향', 'KBS 뉴스 9', '톱10 시절')는 시각 단서가 아니라 활동 단서(TV 시청 등)로만 쓴다. 편성 시각은 외부 지식이므로 쓰지 않는다. '매일 정해진 시간에'는 시각이 아니라 빈도 단서(`D`)다. 한글 숫자 시각('여섯 시')은 탐지와 건수 보고만 하고 v1에서 쓰지 않는다. ⑤ 빈도어 환산(설계 상수): 매일 7회/주, 거의 매일 5~6회/주, 주 N회·번 N회/주, 매주·주말마다 주말 1회, 가끔·종종·때때로 주 0~1회(시드로 결정), 한 달에 N번은 주당 N/4 확률. ⑥ 추출 방식: 규칙 기반 v1(로컬 실행, 외부 서비스·유료 의존성 없음). 품질은 [DR-20](#dr-20--품질-합격선과-보관)의 표본 검수로 판정한다. ⑦ 대표 지표: "근거 있는 시간 비율" = 시각 근거(등급 A/B/C)가 붙은 활동 슬롯 수 ÷ 전체 슬롯 수를 실행마다 보고한다.
- 분류/근거: ASK, 사용자 위임('전부 해결해', 2026-10-30). 실측(서울 185,228명): 주말·일주일·매주·주N회 표현 172,296명(93.0%)에 비해 숫자 시각은 3,512명(1.9%), 시간대어+N시는 2,699명(1.5%)이고, 숫자 시각 무작위 40건 중 10건 안팎이 방송명 등 비시각이다. '밤'을 빼면 시간대어 보유자는 59.9%다. '매일|하루마다' 문장 중 희망 마커형 비율은 hobbies 2.1%, sports 5.4%, arts 8.6%, family 10.4%, professional 28.3%, career_goals 31.8%이고, 마커에 걸리지 않은 career_goals 표본 대부분도 가치 진술이었다. culinary 등은 아직 측정하지 않아 Tier B로 둔다.
- 대안: 시각 정규식 중심 설계 — 시각 단서가 1.5%라 기각; 모든 필드를 같은 신뢰로 취급 — career_goals와 professional의 목표 진술을 습관으로 오인하므로 기각; LLM·ML 추출 — 외부 의존, 비용, 재현성 문제로 v1에서 기각.
- 날짜: 2026-10-30

## DR-16 — 활동 분류 체계

- 결정: 계획과 프레임의 활동은 아래 15개 대분류(`activity_code`)와 원문 라벨(`activity_detail`)로 표현한다.

| 코드 | 이름 | 포함 예 |
|---|---|---|
| SLEEP | 수면 | 밤잠 |
| REST | 휴식·낮잠 | 낮잠, 멍때리기, 티타임, 명상 |
| MEAL | 식사·음주 | 집밥, 외식, 카페, 맛집 탐방 |
| PERSONAL | 개인관리 | 세면, 목욕·사우나, 미용실, 피부관리 |
| WORK | 근무·생업 | 직무, 가게 운영, 부업, 구직 |
| STUDY | 학습 | 자격증, 어학, 강의 |
| HOUSEHOLD | 가사 | 요리, 청소, 가계부, 빨래 |
| CARE | 돌봄 | 육아, 손주 돌보기, 간병, 반려동물 돌봄 |
| MOVE | 이동 | 출퇴근, 장소 간 이동(C-06이 생성) |
| EXERCISE | 운동·산책 | 산책, 등산, 헬스, 배드민턴 |
| HOBBY | 취미·여가 | 게임, 영상 시청, 독서, 텃밭, 공예 |
| SOCIAL | 사교·모임 | 친구 만남, 동호회, 경로당, 종교 모임 |
| CULTURE | 문화·관람 | 전시, 공연, 고궁 탐방, 경기 관람 |
| ERRAND | 용무·쇼핑 | 장보기, 병원, 관공서, 은행 |
| OTHER | 기타 | 분류 불가 |

- 사상 규칙: 키워드 기반이며 우선순위 순서를 규칙 버전에 고정한다. 매체 키워드('영상·시청·감상…')를 여행 키워드보다 먼저 판정한다(예: '유튜브 여행 영상 시청'은 HOBBY). 후보당 대분류 1개, 원문 라벨은 `activity_detail`에 보존하며 사상 불가는 OTHER다. 여행·캠핑 같은 서울 밖 외출은 분류가 아니라 [DR-12](#dr-12--서울-밖-활동의-범위와-판정)의 생략 판정으로 처리한다. 목표: 취미 목록 항목의 OTHER ≤ 10%(출현 횟수 기준). 프로토타입 키워드 규칙 14묶음으로 5.5%를 실측했다. 사상 정확도는 [DR-20](#dr-20--품질-합격선과-보관)의 표본 검수로 따로 잰다.
- 분류/근거: ASK, 사용자 위임('전부 해결해', 2026-10-30). 취미 목록 821,207건 중 고유 문자열이 236,628개이고 73.8%가 1회만 나오며 상위 500개가 25.8%만 설명하므로 원문 라벨 그대로는 집계와 충돌 검사가 불가능하다. 프레임의 `activity_code`는 외부 계약(출력 스키마)이다.
- 대안: 원문 라벨 그대로 — 집계 불가로 기각; 세분류 50개 이상 — v1 규칙 유지 비용 과다로 기각(필요하면 후속 DR로 세분).
- 날짜: 2026-10-30

## DR-17 — 프레임과 시간 규약 및 결정성

- 결정: ① 시간: KST(Asia/Seoul, UTC+9, 일광절약 없음). 하루는 00:00부터 23:50까지 10분 간격 144개 시각이다. ② 프레임 의미: 시각 t의 순간 상태(t에 진행 중인 세그먼트). ③ 세그먼트: [start, end) 반열린 구간이고 start·end는 모두 10분의 배수, 길이는 10분 이상이다. 인물의 세그먼트는 기간 전체를 겹침과 공백 없이 덮고 날짜 경계(00:00)에서 나눠 저장한다(자정을 넘는 수면은 두 개). ④ 이동: 장소(집·근무지·기타)가 바뀌면 MOVE 세그먼트를 둔다. 구가 바뀌는 MOVE는 20분 이상(10분 배수), 같은 구 MOVE는 10분이다. ⑤ 이동 중 귀속([DR-11](#dr-11--이동-중-지역-귀속) 보완): MOVE [s, e)의 중점 m = s + (e − s)/2에서 [s, m)은 출발 구(`MOVE_OUT`), [m, e)는 도착 구(`MOVE_IN`)다. 중점 시각은 후반(도착 구)에 속한다. 10분 눈금에서 10분 MOVE는 출발 구 1프레임만 남으므로 구가 바뀌는 MOVE를 20분 이상으로 해 출발·도착 프레임이 각각 하나 이상 생기게 한다. ⑥ 결정성: 계획은 (원본 행, 규칙 버전, 시드, uuid, 날짜)의 순수 함수다. 난수는 (시드, uuid, ISO 주, 요일) 키의 독립 스트림에서만 뽑으며, 처리 순서·분할·병렬도·재시작과 무관하게 같은 결과를 낸다. 자정 이어짐은 전일 계획의 마지막 세그먼트를 읽어 처리한다(전일 계획도 순수 함수이므로 재계산할 수 있다). ⑦ 프레임 행(개념): `ts`, `district`, `uuid`, `activity_code`, `activity_detail`, `state_kind`(`ACTIVITY`/`MOVE_OUT`/`MOVE_IN`), `segment_id`.

## DR-18 — 저장과 조회 방식

- 결정: 정본은 세그먼트(인물×구간)이고 프레임은 세그먼트에서 계산하는 파생 뷰다. 세그먼트는 날짜 단위 Parquet로 보관한다(열: `uuid`, `date`, `start`, `end`, `kind`(`ACTIVITY`/`MOVE`), `activity_code`, `activity_detail`, `district`, `from_district`, `to_district`, 출처 라벨, 근거 참조, `rule_version`, `seed`; 열 구성은 구현체 Map에서 확정). 프레임은 요청 범위에서 시각 1개(185,228행)씩 청크로 계산해 스트리밍하고, 필요하면 일 단위 Parquet(시각·구 순 정렬)로 내보낸다. 전체 프레임을 메모리에 동시에 보유하지 않는다. - 대안: 프레임을 정본으로 저장 — 중복과 용량 과다로 기각; JSON·CSV — 크기와 타입 손실로 기각; 구마다 파일 — 작은 파일 폭증으로 기각.

## DR-27 — 장소가 불확실한 명동 상호명

- 결정: 명동이라는 지명 및 명동성당·명동역점의 언급뿐 아니라, 명동교자·명동삼겹살·명동집처럼 상호명에 명동이 들어간 행도 본 결과에 포함한다. 상호만 언급한 4건은 명동 소재가 확인된 것으로 취급하지 않으며 메타데이터에 식별자를 따로 기록한다.
- 분류/근거: ASK, 사용자 확정. 사용자가 ‘본 결과에 포함: 이름에 명동이 들어간 상호까지 넓게 포함하지만 실제 위치는 불확실합니다’를 선택했다.
- 대안: 상호명만 나온 행을 본 결과에서 제외하고 별도 검토 대상으로 보관하는 방법은 기각했다.
- 날짜: 2026-10-31

## DR-28 — 명동 추출 방식과 산출물

- 결정: 고정된 서울 원본의 25개 문자열 필드를 검사하여 확인된 명동 지명·시설·상호 토큰을 찾는다. 사람 이름과 광명동·광명동굴은 제외한다. 원본 순서·26개 열·값·타입을 유지한 Parquet을 정본으로 만들고, 열람용 CSV와 출처·판정 근거 메타데이터를 함께 저장한다.
- 분류/근거: SELF. 사용자가 지정한 범위를 고정 원본에서 재현하는 내부 선택이다. 데이터의 실제 토큰을 전수 확인하고 독립적인 경계 검사로 결과를 대조한다. CSV는 편의 사본이며 Parquet이 타입을 보존한다.
- 대안: `명동` 부분 문자열만 찾기(광명동굴·사람 이름 오탐); 중구만 선택하기(다른 구 거주자의 명동 활동 누락); 원본 파일 덮어쓰기(불필요한 손상 위험)는 기각한다.
- 날짜: 2026-10-31

## DR-24 — 명동 지형 자료의 종류와 범위

- 결정: 지면 고도만 수집한다. 범위는 서울특별시 중구 **명동 행정동 전체**(행정동코드 `1114055000`)다. 도로와 건물 데이터는 수집하지 않는다.
- 분류/근거: ASK, 사용자 확정(2026-10-31). 사용자가 제시된 선택지 중 ‘지면 고도만’과 ‘명동 행정동 전체’를 각각 선택했다.
- 대안: 고도와 도로·건물 병행, 도로·건물만 수집; 명동역·명동성당 중심의 임의 범위, 명동 주변의 더 넓은 범위는 선택하지 않았다.
- 날짜: 2026-10-31

## DR-25 — 고도·행정동 경계 자료의 출처와 조건

- 결정: 지면 고도는 공개 [GEDTM30 v1.2](https://doi.org/10.5281/zenodo.18887460) 1초각 DTM을 사용하고, 명동 경계는 [vuski/admdongkor](https://github.com/vuski/admdongkor)의 2026-10-01 행정동 경계에서 `1114055000`을 선택한다. GEDTM30과 가공 경계는 CC BY 4.0이며 경계의 원출처 SGIS 표기를 유지한다.
- 분류/근거: ASK, 사용자 확정(2026-10-31). 약 30m·2006~2015년 기반 추정값이며 출처표시 조건이 있음을 안내한 뒤 GEDTM30과 공개 행정동 경계 사용을 선택했다.
- 대안: 사용자가 별도 원본을 지정하는 방법은 선택하지 않았다. GEDTM30은 건물의 영향을 최소화한 지면 추정치이며 현장 실측이나 최신 상세 지형이 아니다.
- 날짜: 2026-10-31

## DR-26 — 지형 자료의 저장과 검증

- 결정: 경계와 교차하는 원본 격자를 재표본화 없이 보존해 EPSG:4326 GeoTIFF로 저장하고(`all_touched=True`), 선택한 경계 GeoJSON·메타데이터·이용 안내를 함께 둔다. 고도 원본의 버전·ETag와 경계 원본 커밋·SHA-256을 기록하며 최종 산출물 SHA-256 및 재독 검증을 수행한다. 기존 데이터와 활동 엔진에는 연결하지 않는다.
- 분류/근거: SELF. 공개 GIS 표준과 원본 보존을 따른 재현 가능한 저장·검증 방법이며, 바꾸기 쉽고 사용자가 확정한 자료·범위를 바꾸지 않는다. 교차하는 경계 격자는 일부가 행정동 밖으로 확장될 수 있음을 안내한다.
- 대안: 보간이나 세밀한 격자 생성은 원본에 없는 정밀도를 암시하므로 제외한다. 행정동 바깥 값을 전부 남기는 사각형 저장은 범위 식별이 어렵기 때문에 제외한다.
- 날짜: 2026-10-31

## DR-29 — 페르소나 증강의 인물 정체성

- 결정: 명동 관련 원본 514명을 각각 새로운 가상 인물들의 부모로 사용하고, 나이·가구·직업 등도 공식 사회통계에 맞게 변경한다. 각 변형은 원본과 연결하고 명동 관련 맥락과 출처를 유지하며 서술과 구조화 속성의 일관성을 검증한다.
- 분류/근거: ASK, 사용자 확정. 사용자가 ‘새 가상 인물로 변형’ 선택지를 선택했다. 원본 514명의 고정된 속성 분포를 단순 복제하는 경우 사회통계 보정이 어렵다.
- 대안: 원본의 인구통계·가구·직업을 고정하고 생활만 변형하는 방식은 기각했다.
- 날짜: 2026-10-31

## DR-30 — 증강의 기준 모집단과 통계

- 결정: 서울 거주자를 기준 모집단으로 삼고, 실제로 확보 가능한 중구·명동 관련 사회통계를 별도로 반영한다. 전국 통계는 서울 세부 통계가 없는 경우 범위·기준연도·한계를 명시한 참고 자료로 사용한다.
- 분류/근거: ASK, 사용자 확정. 사용자가 ‘서울 거주자 중심 + 활용 가능한 중구·명동 통계’를 선택했다. 이는 명동 방문객 전체의 대표 표본이라는 뜻이 아니다.
- 대안: 명동 상주·방문 인구 전체만 대상으로 맞추거나 한국 전체 인구를 주 목표로 하는 방법은 선택하지 않았다.
- 날짜: 2026-10-31

## DR-31 — 증강 설명의 구성과 온톨로지 연계

- 결정: 새 인물은 동일 데이터셋의 일관된 서울 페르소나를 사회통계에 맞춰 활용하고, 각 인물에 514개 원본 중 하나의 명동 관련 단서와 출처를 연결한다. 동시에 진행 중인 페르소나 온톨로지의 확정된 개념·속성·관계 계약을 확인해 결과에 반영한다.
- 분류/근거: ASK, 사용자 확정. 사용자가 ‘1번으로 하는데, 지금 claude가 이어하는중인 온톨로지를 반영해야해’라고 답했다. 기존 자유서술의 이름·나이·가구·직업을 임의로 바꾸면 설명과 속성이 충돌할 수 있다.
- 대안: 514개 원문의 모든 서술을 새 속성에 맞게 일괄 재작성하는 방식은 선택하지 않았다. 원본의 모든 성격·취미가 그대로 복제되지는 않는다는 점을 전제로 한다.
- 상태: Claude의 [온톨로지 초안 §7.1](01a_persona_ontology.md#71-명동-인물-증강dr-31)의 최소 연결 계약을 확인해 적용했다. 최종 특성 스키마와 반응 함수는 미확정이므로 그 부분의 실행 호환성은 아직 검증할 수 없다.
- 날짜: 2026-10-31

## DR-90 — 명동 고도의 대화형 3D 표현

- 결정: 사용자가 요청한 3D 시각화의 입력은 기존 명동 행정동 지면 고도 GeoTIFF와 메타데이터로 한다. 각 유효 격자를 원래 높이를 가진 면으로 표시하고 결측은 생략한다. 수평 거리를 미터로 투영해 수직 배율 1×로 보이며 회전·확대·고도 조회를 제공한다. 외부의 건물·도로·새 고도 자료를 추가하지 않는다.
- 분류/근거: ASK → 사용자 요청으로 확정(기존 명동 지면 고도의 3D 시각화). 수직 비율 1×·결측 제외·원본 유지 및 대화 내 인터랙션은 데이터를 왜곡하지 않는 SELF 표현 결정이다.
- 대안: 수직 높이를 임의로 과장하거나, 외부 건물·도로를 만들어 넣는 방식은 선택하지 않는다.
- 날짜: 2026-10-31

## DR-100 — 역산 엔진과 온톨로지의 연결 범위

- 결정: 범용 정방향·역산 엔진을 설계하고 명동 페르소나 온톨로지는 어댑터로 연결한다. 이번 요청의 산출물은 알고리즘과 Map 설계다.
- 분류/근거: ASK → 사용자 확정. 사용자가 ‘범용 엔진 + 명동 어댑터 (추천)’를 선택했다. 기존 온톨로지의 개념·속성·관계를 보존하면서 다른 도메인에도 같은 역산 계약을 적용할 수 있다.
- 기각된 대안: 명동 온톨로지에 전용 엔진을 결합하는 방법.
- 미해결 실행 입력: 실제 명동 온톨로지 스키마 및 실행 가능한 전이 규칙의 위치. 범용 계약 설계는 진행하며 실제 어댑터 연결 검증은 이 입력이 있어야 한다.
- 후속 확인: [DR-107](#dr-107--명동-온톨로지-초안과의-계약-대응)에서 초안 경로를 확인했다. 최종 스키마·수치·실행 코드는 여전히 미확정이다.
- 날짜: 2026-10-31

## DR-101 — 역산에서 변경할 수 있는 값

- 결정: 조절 가능한 외부 변수만 역산한다. 날씨 등 조절 불가능한 외생 조건은 시나리오 입력으로 고정해 평가하며, 모델 계수·난수·초기 상태를 목표에 맞추기 위해 함께 조작하지 않는다.
- 분류/근거: ASK → 사용자 확정. 사용자가 ‘조절 가능한 변수만 역산 (추천)’를 선택했다. 결과는 실행 가능한 변경안을 탐색하는 의미를 갖는다.
- 기각된 대안: 조절할 수 없는 조건까지 자유변수로 풀어 가능한 상황의 조합을 제시하는 방식.
- 날짜: 2026-10-31

## DR-102 — 목표 일치와 해의 선택 기준

- 결정: 선택한 핵심 지표를 명시적 허용오차 안에서 맞추는 것을 우선하고, 이를 만족하는 해 가운데 기준 외부 값으로부터의 변경량을 최소화한다. 해를 찾지 못하면 가장 가까운 후보와 지표별 미달량을 반환하고, 탐색 실패와 도달 불가능의 증명을 구별한다.
- 분류/근거: ASK → 사용자 확정. 사용자가 ‘핵심 지표 + 최소 변경량 (추천)’를 선택했다. 전체 개인 상태를 동일하게 재현하거나 실제 금전 비용을 최소화하는 계약은 채택하지 않는다.
- 기각된 대안: 실제 비용 최소화(비용 함수 필요), 모든 시간별 상태의 완전 동일성(선택한 목표보다 강한 조건).
- 미해결 실행 입력: 지표·집계 구간·목표값·허용오차·조절 변수의 허용 범위와 변경량 척도. 범용 엔진은 이 값을 요청마다 명시적으로 받으며 임의의 도메인 값을 기본값으로 만들지 않는다.
- 날짜: 2026-10-31

## DR-91 — 3D 격자 이음면과 접근 가능한 조작

- 결정: 서로 인접한 유효 격자의 공통 변에 두 셀의 원본 높이를 잇는 수직 면을 표시해 3D 지형이 시각적으로 끊기지 않게 한다. 격자 윗면의 원본 값은 변경하거나 보간하지 않으며, 결측 격자에는 면을 만들지 않는다. 드래그·확대 외에 키보드로 조작할 수 있는 방향·확대 범위 입력을 제공한다.
- 분류/근거: SELF. 시각화 미리보기에서 높이가 다른 평면 격자 사이의 틈 때문에 지형이 분리되어 보였고, 작은 화면의 축 배치도 정리가 필요했다. 이음면은 두 원본 셀만 연결하는 표현이며 데이터 자체는 수정하지 않는다.
- 대안: 원본에 없는 새로운 고도 격자를 생성하거나, 결측 영역을 메우는 보간 방식은 제외한다.
- 날짜: 2026-10-31

## DR-92 — 좁은 화면의 3D 축 표시

- 결정: 화면 폭이 480px 미만일 때는 화면에 잘리는 3D 축을 숨기고 고도 범위·단위와 출처를 유지한다. 넓은 화면에서는 동쪽·북쪽 거리와 고도 축을 표시한다. 방향·확대 입력과 각 격자의 고도 조회는 유지한다.
- 분류/근거: SELF. 브라우저 폭 320px 검사에서 3D 축이 겹치고 잘리는 문제가 확인됐으며, 반응형 표시만 바꾸고 데이터·측정 단위·사용자 선택은 바꾸지 않는다.
- 대안: 글자를 읽을 수 없을 정도로 축소하거나, 작은 화면에서 가로 스크롤을 허용하는 방법은 제외한다.
- 날짜: 2026-10-31

## DR-93 — 3D 색상의 화면 테마 대응

- 결정: 고도 색상과 축·격자는 화면 테마의 색상 토큰으로 계산하고 테마 변경 시 갱신한다. 고도의 최소·최대와 색상 대응은 테마에 관계없이 유지한다.
- 분류/근거: SELF. 데이터와 해석을 바꾸지 않는 가독성·접근성 처리다.
- 대안: 고정된 밝은 화면 색은 어두운 화면에서 가독성이 나빠질 수 있어 제외한다.
